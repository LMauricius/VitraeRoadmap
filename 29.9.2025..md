# Vitrae Development roadmap

## [Goal] Game-ready 3D engine
The core idea of VitraeEngine is for it to be ready both for graphics research
and for production software.
It's necessary to implement a couple key features that will cover 
all traditional use-cases for a pure graphics engine.

### [Feature] Animation system
The ideal animation system is modular and tied to assets that intuitively support animation.
It has to support skeletal animations, mesh-morphing animations
and dynamic animations such as inverse kinematics.

1. [Task] High-level design of animation system
2. [Task] Programming interface for the system
3. [Task] Implementation of a modular system
4. [Task] Implementation of common methods as examples

### [Feature] Smart scene graph
The current scene system is a placeholder for something bigger.
There is a way to design a scene graph that does't require much thought about the structure
but is fast and flexible:
- The scene is just a list of all objects (called props)
- The engine automatically builds a suitable structure - key for performance

The scene itself is a trivially simple hierarchical database - it's just a list of props. Of course, some props are used as a subscene to increase reusability. Each subscene could have multiple levels of detail (LoDs) and usage profiles.

## [Goal] Inventive graphical programming features
VitraeEngine was created with graphical advancements as a first-class usage goal.

### [Feature] Tensor buffers
By leveraging the flexibility of the hardware rasterizer and texture sampling,
we can enable more memory manipulation and compression features for some buffers.
These texture element based buffers will be called `TensorImages`
due to them being structures of scalars and vectors.

### [Feature] Updated workgraph system
The current pipeline system is limited, and often needs workarounds to achieve desired behavior.
Most importantly, the argument setting and redirection system needs an overhaul.

#### [Task] Rename and abstraction
Current:
- Method is a collection of definitions
- Task is an abstract definition of behavior
- Pipeline just references tasks, which are mostly stateless

Desired:
- Method         -> Solution
- Task           -> Method
- Task reference -> Task
- Pipeline allocates tasks, which can be copied to a big enough buffer for cache optimization.

#### [Task] More flexible redirection system
Having a single alias map per the pipeline, along with special "Adaptor" classes is unwieldly.
Implement a more flexible mapping system that simultaneously supports:
- setting values directly to the params
- redirecting to another param (as it is now)
- subtasks, per the mapping instead of only per Solution

The new system should be settable per each Method, not just per pipeline and Adaptor methods.
The dependency mapping should apply retroactively, so a dependency map also sets the redirections
for the dependencies of dependencies. This fully replaces the need for Adaptor methods.

#### [Task] Streaming value system
Streaming of data feels natural for a pipeline system. The current system provides no support for streaming.
Pipelines are generated as single-pass, fully linear lists of interdependant tasks.
Streaming of results and processing them should make dynamic object lists and selections or draw commands simpler.
